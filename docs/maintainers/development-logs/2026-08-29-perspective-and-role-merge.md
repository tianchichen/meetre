# 2026-08-29 视角切换、角色合并与标题层级

## What This Phase Tried To Solve

上一阶段做出了单屏天平和四态模型，但页面仍然只讲一个故事。用户提出五处调整，指向三个真问题：

1. 页面假设读者是组织者。参会者要的判断完全不同——「我这个角色在这场会里是否必要」——而页面既没有切换，也没有回答这个问题的位置。
2. 左盘假设角色数等于人数。现实里一个人常兼几个角色（2 个角色实际只来 1 个人），页面把他画成两个方块，成本也算了两遍。方块本身也不像人。
3. 标题区把四个大数字并列堆在一起，谁都不主导；会议名反而占了最大的字号——但会议叫什么不影响该不该开，评估才是主要信息。

## What Was Completed

- **视角切换**成为一等控件（顶栏，不是设置项）。组织者视角讲全盘规划；参会者视角的 h1 直接回答该不该来：`你必须在场` / `你只需要来一段` / `你不必到场`，由 `myAssessment()` 按「有没有议题把我列为必要角色」和「相关议题是否覆盖整场」推出。`data.perspective` 只决定初始视角，之后是页面状态。红色态例外：底线被破时两个视角都先说底线，也都不生成可发出的文案。
- **CTA 随视角换主语**。组织者按状态（按建议调整 / 改发一条异步更新 / 发出这个邀请），参会者按自己的必要性（请辞并提议异步 / 提议只参加相关议题 / 确认参加），多数分支带一个次选动作。切视角会收起草稿——一份写给组织者的邀请，换到参会者视角就不该继续挂在那里。
- **角色可合并**。角色行的「并入…」把一个单人角色并入另一个角色，宿主的第一个人形叠一枚角色计数徽标，下面出现「由 X 兼任 / 拆开」。合并减少人数和成本，但**不能绕过必要角色底线**：`breaches()` 和 `repairBreaches()` 都经 `hostRoleOf()`，比的是兼任者的同步人数；把兼任者移出会议立刻算破底线，提示写明「由『决策者』兼任」。
- **方块换成人形图标**。必要 / 可有可无用字重加下划线区分，不用色相——底色本身就是状态色，第五种色相会被它吃掉。异步知会是空心，无需参与是虚线描边。
- **标题区重排主次**：会议名退成一行小眉标题，判词是唯一的 h1，接一句**不重复判词措辞**的理由，然后是一个主数字（集体成本）配三条共用同一把尺子的对比长条（原始 / 当前 / AI 推荐，最长者为 100%，推荐那条用斜纹区分）。取代了四个并列大数字。
- **天平上的字号调大**：角色名和议题名 12.5px → 14px，分钟数与步进器同步放大。
- **模板拆成 13 个片段**。交付物仍是单个离线 HTML（零外链、不 fetch），但源码按职责分在 `assets/report/` 下，renderer 按固定顺序拼装（顺序即依赖顺序）。这解掉了上一阶段留下的 955 行超限问题：现在每片都在 800 行内，并由测试遍历目录钉死。

## Detours And Lessons

**我的测量脚本错了，页面是对的。** 净空脚本用梁的旋转后包围盒高度（231px）当梁厚，于是每个倾斜状态都算出净空 ≈ −60 并打印 BAD。改用 `beamEl.offsetHeight`（11px）、以梁的中线为支点后，所有数字转正。上一阶段刚学到「视觉几何必须测量」，这次的补充是：**测量工具本身也要验证**——先用一个已知正确的状态（水平梁）校准，再去量未知的。

修正后的测量随即暴露了一个真 bug：参会者面板一出现，`.report` 内容就超过容器高度，而 `justify-content: center` 会把超出部分从**两端**一起裁掉，h1 顶边跑到 −29px。改成上下两个 `flex: 1 1 0` 的空白项来居中——没有余量时它们自然收成 0，内容改为顶对齐。

**同一个裁切问题我修了两次才修对。** 第一次用 `.report { overflow-y: auto }` 兜底，测量显示不再裁 h1，就算过了。截图才看出参与方式那一整行没了：它掉进了一个没有任何视觉提示的内层滚动区——没裁掉，但也没人能发现它。真正的修法是承认「一屏读完」是目标而不是硬约束，把 `.page` 的 `height: 100dvh` 改成 `min-height`，装不下就整页滚动。仓库里其实早有这个先例（草稿展开时就是这么做的），我却在旁边新造了一个内层滚动区；把它提升为基础行为后，`data-drafting` 和 480px 断点里的相关规则都成了重复代码，一并删掉。**测量能证明「没有被裁」，但证明不了「能被看见」。**

内容重复也是同类问题的另一面。修完裁切后截图显示同一句话出现三遍（h1、导语、面板判词、面板理由），因为 `statusSentence()` 一直把 h1 的措辞抄进导语，而参会者面板又独立渲染了一遍判断和理由。这正是用户说的「字太堆叠、没有主次」——我在标题区解决了它，却在新加的面板里重新造了一遍。现在导语不复述 h1，面板只讲能落地的事实（我是谁、几条同步议题与我相关、我选哪种参与方式）。

原生 `<select>` 也值得一提：不加 `appearance: none` 它会带一整套灰色系统外观，在会随状态变色的底色上就是一块脏斑；而不能合并的角色留一个 disabled 的空框，只是让每行看起来都有个坏掉的按钮——直接不给控件更干净。

## Still Uncertain

- 参会者在蓝色态是否也该有次级出口（上一阶段留下的问题，仍未决）。
- 平衡态梁完全水平是否该给一个极小残余倾角（同上）。
- 窄屏双盘并排把名字压得很窄，是否改成上下两盘仍未设计。参会者视角在窄屏下已需滚动，这是设计选择，不是缺陷。

## Next Candidates

- Schema v2 的每议题角色出席/知会映射（连续三个阶段都指向它了）。现在 `myAssessment()` 只能用 `requiredRoleIds` 推断「我是否必要」，拿不到完整参会名单，所以「相关议题」的判断偏保守。
- 合并目前只允许单人角色并入、且不允许套娃（不能把已有兼任的角色再并入别处）。真实场景里三角色一人兼任是存在的，要支持得先决定徽标和「由谁兼任」这行怎么表达链式关系。
